# Architecture rules

- Signup QR/manual selection is presentation-only and shares the existing UPI value, decoder and validation. Why: changing the visible option must not change payout or signup requirements.

- Worker localization uses i18next resources and display-only helpers in `src/i18n/display.ts`; never translate stored IDs, RPC inputs, comparison strings or server contracts. Why: language selection must not change booking, payout or authentication behavior.
- Worker language is subscribed through React and persisted in localStorage plus Capacitor Preferences before initial rendering. Why: switching must be immediate and survive logout and native restarts.

- Booking offer lifecycle is logged append-only in `booking_offer_events` (unique per booking_request_id + event_type): device events via the `ack-booking-delivery` edge function, server events (push_sent, final status) via a trigger on `booking_requests`. Why: one deduped, auditable timeline per offer without touching dispatch or acceptance logic.
- Offer telemetry is fire-and-forget and must never block or alter Accept/Reject; accept/reject RPCs remain the sole authority for assignment. Why: telemetry failures must not cost workers bookings.
- Worker rejections go through `reject_booking_offer` (worker taken from the session server-side, refuses expired/assigned offers, idempotent); the legacy `reject_booking_request` is a guarded wrapper that refuses a supplied worker id that differs from the session, and the tier logic lives in service-role-only `_reject_booking_request_core`. Clients show "rejected" only on `confirmed: true`. Why: no client may name another worker or claim an unconfirmed rejection.
- OTP V2 client logic lives in `src/lib/otpV2.ts` + `src/lib/otpCompletionFlow.ts` behind a rollout switch (off = original legacy lifecycle). Legacy completion is reachable in V2 mode only when the same gateway answer is LEGACY_BOOKING; the per-booking mode cache is memory-only, short-lived and display-only. Why: a stale or guessed mode must never authorize the legacy path.
- Frontend tests run with `bun run test` (vitest, jsdom). Why: OTP safety scenarios are covered by mocked-gateway tests.
- Worker App booking reads use `WORKER_BOOKING_COLUMNS` (never `select("*")` on bookings) and the Worker booking type omits `completion_otp`. Why: workers must never load customer OTP values, and a later server-side lock on that column must not break worker reads.
- First-time setup decisions (setup gate, booking-channel classification, optional-popup "Continue with notifications", battery "Later", one-time movement request) live as pure functions in `src/lib/setupGate.ts`; the gate re-reads real OS status (permission + booking channel) every check, and the popup-declined choice is memory-only per session, never a "granted" flag. Why: opening Settings or a stale flag must never count as granted, and missing popups must not trap workers.
- Worker reachability rules (connection vs availability vs eligibility, proposed watchdog/dispatch rules) live as pure display-only functions in `src/lib/workerReachability.ts`; backend changes are specified in docs handoffs, never edited under `supabase/functions/` from this project. Why: saving a function file auto-deploys it to production.
- Worker Focus diagnostics rules live as pure functions in `src/lib/workerDiagnostics.ts`; events queue on the phone in `src/lib/diagnosticsSync.ts` and stay local until `DIAGNOSTICS_SERVER_SYNC_ENABLED` is turned on after the staged receiver is approved. Why: diagnostics must never write to production or change availability before backend approval.
- Delivery confirmations (push_received, popup_shown, worker_seen) authenticate with the signed ack_token first; on 401/403, missing or expired token they retry once with the worker's Supabase session JWT (no ack_token, no worker_id); Accept/Reject taps never use the fallback. Why: the receiver must derive identity from a verified login, never from a phone-supplied id.
- Worker App update decisions come only from the Admin Panel RPC `get_app_update_decision` (worker/android, installed numeric build), parsed and safety-checked in `src/lib/updateDecision.ts` (malformed/unknown → none, store link must be the official package, force deferred during active bookings); the native Play in-app update trigger stays disabled. Why: one server authority prevents overlapping or wrong-listing prompts and never locks workers out.
- App icons are generated from `branding/app-icon-master.png` by `scripts/generate-app-icons.sh` (`bun run icons:generate`); never hand-edit generated icon files. Why: one master keeps launcher, web and store icons identical.
- 4-digit Start OTP (worker) calls only the DB RPC `verify_start_otp` via `src/lib/startOtp.ts`; which button shows is decided per booking by the server flag `start_otp_required` (unflagged = legacy End OTP unchanged), and the End OTP screen redirects flagged unstarted bookings to Start. Worker identity comes from the session, the code is never logged/stored, and "started" is only read back from the server. Why: the server is the sole authority for starting a booking.
- Mandatory-availability rules (what counts as a real slot, ON gating, setup redirect) live as pure functions in `src/lib/availabilityGate.ts`; the ON switch re-reads saved slots at tap time and placeholder values never count. Why: a worker must never go ON without real saved slots, and cached or junk data must not decide it.
- Home training video rules: pure functions in `src/lib/trainingVideo.ts` behind `TRAINING_VIDEO_CLIENT_ENABLED` + admin-only `worker_training_video_settings`; read-only, hidden on OFF/error/offer/active booking/background, iframe unmounted to stop audio. Why: bookings win and no empty box.
- Start OTP reminders: phone-scheduled local notifications planned in `src/lib/startOtpReminder.ts`, synced by `StartOtpReminderManager`; only server `started_at`/status/worker_id stop them; never touch OTP, dispatch or payments. Why: survive a closed app without altering bookings.
- Worker reconnection reminder rules live as pure functions in `src/lib/reconnectReminder.ts` behind `RECONNECT_REMINDER_ENABLED`; only true foreground opens count, token problems go to admin follow-up, and nothing may change availability. Why: reminders must never alter dispatch and background wakes must not fake an app open.
- Late-acceptance refusal (P0001 `BOOKING_ACCEPTANCE_CLOSED:`) is recognised only by `src/lib/acceptanceClosed.ts` (web) and the same prefix check in the native alert/overlay; it closes the offer, clears the queue, never retries, and touches no OTP path. Why: the server alone decides operating hours; the app only reacts.
- Accept decisions go through `src/lib/acceptOutcome.ts` (won/closed/gone/retry) and the device-wide claim in `src/lib/deviceAcceptLock.ts` (JS coordinator + native `OfferQueue` via OverlayPlugin `claimAcceptance`); retryable failures keep an unexpired offer open. Why: one Accept per booking per phone and network blips must not cost workers bookings.
- Offers arrive only via booking_requests realtime, FCM and `useBookingPollingFallback` (single backup poller, also on resume/reconnect). Why: duplicate pollers waste battery and the old bookings-INSERT listener bypassed dispatch order.
- Notification health rules: `src/lib/pushHealth.ts`; phone/server token mismatch = unhealthy. Why: stale tokens silently miss alerts.

- Worker payout display rules (status mapping, Paid only with server `paid_at`, IST day/week/month, totals from server payout records only, reference from manual_utr/reference_id/external_reference) live as pure functions in `src/lib/payoutDisplay.ts`; every money screen reads through `useWorkerPayouts` (paginated, realtime, foreground refresh). Hybrid payouts read only the four contract-v1 RPCs through `src/lib/hybridPayoutApi.ts` (strict validation, no worker id sent, server labels shown) and `HybridPayoutSection` renders nothing when `HYBRID_PAYOUT_UI_ENABLED` is off or any response fails. Why: one rule set keeps all screens identical and the app never invents payout data.
- Worker account linkage is server-only: the app never writes `workers.id`/`user_id`/`phone` or re-links by phone; recovery codes are recognised only by `src/lib/workerLinkage.ts`, and the staged DB guard/recovery RPC lives in `docs/security-fixes-2026-11-10/worker-linkage/`. Why: a matching phone number must never hand a worker's bookings and payouts to another login.
- Availability screen spoken help lives in `src/lib/availabilityVoice.ts` (player + engines: phone text-to-speech plugin when the installed app has it → browser speech → English fallback) and `useAvailabilityGuide`; it plays only on tap, a tap while speaking stops it, and it stops on leaving/backgrounding. Why: voice help must never overlap, auto-play, or touch slot saving or dispatch.
- Update safety: "may I interrupt" is decided only by `src/lib/workSafety.ts` (offer, active status, OTP routes, bookings not loaded = busy), shared by Play prompts and OTA; OTA rules in `src/lib/otaSafety.ts` + native `OtaRules.kt` (HTTPS allow-list, SHA-256/size, activate only when idle, failed versions never retried) behind `OTA_DELIVERY_ENABLED`. Why: updates must never cost a booking or OTP step.
- Reported app version/build comes from `src/lib/installedVersion.ts`; heartbeats send the login JWT plus own worker_id. `worker-heartbeat` is recovered production code + watch-only audit (backup in `docs/security-fixes-2026-11-11/update-system/heartbeat-watch-only/`); never deploy the old copy. Why: it drops reachability, token repair and missed-offer recovery.
- Home display rules: `src/lib/homeSummary.ts`; Home cards only read data and hide failing parts. Why: never show unconfirmed readiness or money.

- Practice bookings: local states in `practiceBooking.ts`; push stays off (`PRACTICE_PUSH_ENABLED`) pending approval; sender staging rules live in `docs/test-booking-training-2026-11-11/sender/AGENTS.md`. Native practice messages exit before BackendSync/OfferQueue, bind to the native login, and yield to any real booking message. Why: practice must never touch real bookings, availability, telemetry or payments.
