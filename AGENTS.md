# Architecture rules

- Signup QR/manual selection is presentation-only and shares the existing UPI value, decoder and validation. Why: changing the visible option must not change payout or signup requirements.

- Worker localization uses i18next resources and display-only helpers in `src/i18n/display.ts`; never translate stored IDs, RPC inputs, comparison strings or server contracts. Why: language selection must not change booking, payout or authentication behavior.
- Worker language is subscribed through React and persisted in localStorage plus Capacitor Preferences before initial rendering. Why: switching must be immediate and survive logout and native restarts.

- Booking offer lifecycle is logged append-only in `booking_offer_events` (unique per booking_request_id + event_type): device events via the `ack-booking-delivery` edge function, server events (push_sent, final status) via a trigger on `booking_requests`. Why: one deduped, auditable timeline per offer without touching dispatch or acceptance logic.
- Offer telemetry is fire-and-forget and must never block or alter Accept/Reject; accept/reject RPCs remain the sole authority for assignment. Why: telemetry failures must not cost workers bookings.
- Worker rejections go through `reject_booking_offer` (worker taken from the session server-side, refuses expired/assigned offers, idempotent); the legacy `reject_booking_request` is a guarded wrapper that refuses a supplied worker id that differs from the session, and the tier logic lives in service-role-only `_reject_booking_request_core`. Clients show "rejected" only on `confirmed: true`. Why: no client may name another worker or claim an unconfirmed rejection.
- OTP V2 client logic lives in `src/lib/otpV2.ts` + `src/lib/otpCompletionFlow.ts` behind a rollout switch (off = original legacy lifecycle). Legacy completion is reachable in V2 mode only when the same gateway answer is LEGACY_BOOKING; the per-booking mode cache is memory-only, short-lived and display-only. Why: a stale or guessed mode must never authorize the legacy path.
- Frontend tests run with `bun run test` (vitest, jsdom). Why: OTP safety scenarios are covered by mocked-gateway tests.
- Worker App booking reads use `WORKER_BOOKING_COLUMNS` (never `select("*")` on bookings) and the Worker booking type omits `completion_otp`. Why: workers must never load customer OTP values, and a later server-side lock on that column must not break worker reads.
- First-time setup decisions (setup gate, booking-channel classification, optional-popup "Continue with notifications", battery "Later", one-time movement request) live as pure functions in `src/lib/setupGate.ts`; the gate re-reads real OS status (permission + booking channel) every check, and the popup-declined choice is memory-only per session, never a "granted" flag. Why: opening Settings or a stale flag must never count as granted, and missing popups must not trap workers.
- Worker reachability rules (connection vs availability vs eligibility, proposed watchdog/dispatch rules) live as pure display-only functions in `src/lib/workerReachability.ts`; backend changes are specified in docs handoffs, never edited under `supabase/functions/` from this project. Why: saving a function file auto-deploys it to production.
- Worker Focus diagnostics rules live as pure functions in `src/lib/workerDiagnostics.ts`; events queue on the phone in `src/lib/diagnosticsSync.ts` and stay local until `DIAGNOSTICS_SERVER_SYNC_ENABLED` is turned on after the staged receiver is approved. Why: diagnostics must never write to production or change availability before backend approval.
- Delivery confirmations (push_received, popup_shown, worker_seen) authenticate with the signed ack_token first; on 401/403, missing or expired token they retry once with the worker's Supabase session JWT (no ack_token, no worker_id); Accept/Reject taps never use the fallback. Why: the receiver must derive identity from a verified login, never from a phone-supplied id.
- Worker App update decisions come only from the Admin Panel RPC `get_app_update_decision` (worker/android, installed numeric build), parsed and safety-checked in `src/lib/updateDecision.ts` (malformed/unknown → none, store link must be the official package, force deferred during active bookings); the native Play in-app update trigger stays disabled. Why: one server authority prevents overlapping or wrong-listing prompts and never locks workers out.
