## Authorization
Each public table immediately grants least-privilege service access, revokes clients, enables RLS and adds an explicit service policy. `service_role` bypasses RLS: Edge caller verification remains mandatory. No authenticated/anonymous read or write, no Firebase UID UUID casts, no invented admin bridge. Ordinary admin roles do not get raw table access. Helpers are invoker-rights with qualified names and fixed search_path; EXECUTE revoked from PUBLIC/anon/authenticated.

Immutable history rejects UPDATE/DELETE/TRUNCATE, including service writers; owner/superuser can disable triggers, so protect owner access. Each revision self-reference is same-parent by composite FK; serialized insert triggers require revision 1 then latest+1, matching predecessor and nondecreasing decision time not before the underlying event. Integer genuine ratings 1–5 use utility (rating−1)/4; complaint rows require utility and no rating, are retained for review but excluded from this candidate calculator. SQL integer casts can coerce fractions: the trusted input adapter must reject fractional input BEFORE binding integer values; SQL column typing alone does not prove API validation. Generated duration compatibility and Supabase roles are untested. Grant/schema privileges and runner ownership must be checked in isolation.

## Projection transaction / remaining work
Service adapter must lock worker+version BEFORE loading its snapshot; validate verified ownership manifest, canonical latest upheld revisions, source/ingestion cutoffs, formula/batch/config hashes, sample/onboarding facts and deterministic input hash. Insert immutable calculation history using the unique replay key. Composite FKs enforce formula/config/batch agreement and pointer ID/worker/formula/as_of/revision identity. An AFTER INSERT trigger publishes history in that same transaction. Projection order is lexicographic `(as_of,calculation_revision)`; same-time reviewed correction is latest+1 with a nonempty correction reference, while equal/stale replay cannot replace a newer pointer. Direct service projection inserts/updates must reference latest history; existing-row backward moves are rejected. Unique input replay must return the existing row before issuing a new revision. The trusted adapter still must update onboarding within that SAME outer transaction; no adapter/job consumer is supplied or activated, and its full atomicity is NOT VERIFIED. Forensic older history may be appended but not published. No production scheduler or consumer exists.

## Canonical ingestion contract
Verify source worker identity, booking owner, assigned worker, authoritative assignment generation/accepted timestamp and offer request/worker/booking/generation/round/start before inserting synthetic anchors. Unknown/ambiguous/cross-owned evidence goes to review, never invented matching. Outcome/Fault/Quality triples reference assignment anchors; outcome accepted_at additionally matches the assignment FK; offer opportunities reference their complete offer anchor. Rejected offers need no accepted assignment. Anchors/manifests enforce internal consistency, NOT authenticity of an arbitrary service writer's source_ref/hash. All known-at decisions/intervals used in a batch must lie within its verified watermarks; latest disputed/excluded corrections never fall back to superseded blame. Faults contribute only through canonical R outcomes, never a separate deduction. These are mandatory adapter contracts requiring isolated tests.

Phase 7 quality observations deliberately use the assignment PRIMARY KEY `(worker_id,booking_id,generation)`, just like fault incidents. They store the quality event time, not a copied acceptance time. No accepted timestamp is required or fabricated for a rating. The generation identifies the assignment; a mismatched worker/booking/generation has no matching parent and must fail. Verified source ownership and rating-to-assignment mapping remain mandatory adapter checks, not inferred from a rating value. Pure synthetic tuple tests do not prove database FK enforcement.

## Rollback considerations
Do not execute teardown against production. A failed file rolls back its own transaction, not the preceding committed files: 001–005 are five transactions. Keep every writer/consumer disconnected until all five files and protections are verified. For an approved isolated reset, archive fixture manifests/calculation audit, disconnect consumers and jobs first, then remove only V4 objects in reverse FK order; regenerate from synthetic fixtures. No destructive rollback SQL is supplied to avoid accidental audit deletion. Eventual production rollback disables V4 consumers/pilot independently and retains security adapters and immutable evidence. Never restore broad unsafe grants or rewrite in-flight offers.
