## Guard limitations and test target
These drafts refuse every database except `isolated_v4_fixture` with three matching session assertions: `priority_v4.environment=isolated-synthetic`, matching `priority_v4.expected_database`, and a nonempty approval reference at least 12 characters. Assertions must come from a separately authorized runner after checking an explicit nonproduction connection/owner/identifier and excluding production credentials. They are **not cryptographic proof**: a privileged operator can set them. Typical hosted Supabase databases named `postgres` deliberately fail; do not loosen the guard to make the linked project pass. No runner/settings command is provided or executed here. Hosted adaptation requires a reviewed target-specific deny/allow guard and separate approval.

## Authorization
Each public table immediately grants least-privilege service access, revokes clients, enables RLS and adds an explicit service policy. `service_role` bypasses RLS: Edge caller verification remains mandatory. No authenticated/anonymous read or write, no Firebase UID UUID casts, no invented admin bridge. Ordinary admin roles do not get raw table access. Helpers are invoker-rights with qualified names and fixed search_path; EXECUTE revoked from PUBLIC/anon/authenticated.

Immutable rows reject UPDATE/DELETE, including service writers; owner/superuser can disable triggers, so protect owner access. Config/evidence hash and cross-table revision-chain consistency are server contracts requiring isolated integration tests, not claimed fully enforced here. Stored duration-expression compatibility and Supabase role availability are untested. Grant usage/schema privileges and migration runner ownership must be checked in the isolated harness.

For an approved isolated reset, archive fixture manifests/calculation audit, disconnect consumers and jobs first, then remove only V4 objects in reverse FK order; regenerate from synthetic fixtures. No destructive rollback SQL is supplied to avoid accidental audit deletion.
